1Резюме архитектора

Короткий вердикт до деталей.

Перед нами не «CRUD с прикрученным ChatGPT», а вполне зрелый для хакатона событийно-ориентированный микросервисный стек с чётким владением данными. Система решает задачу учёта ПО: из CSV/агента приходят «грязные» имена процессов, конвейер нормализует их и связывает с каталогом, детерминированный движок считает нарушения и лицензионный баланс, а LLM применяется точечно — там, где детерминированная логика бессильна (неоднозначные имена, разбор текста EULA, вопросы на естественном языке).

Стиль архитектуры

Микросервисы в монорепозитории, «database per service» (логически), событийная шина для тяжёлого импорта, gRPC для синхронных вызовов, nginx как API Gateway, SPA-фронт.

Главная идея

LLM — не источник истины. Модель выбирает из готовых кандидатов, вызывает разрешённые инструменты и оформляет ответ. Считает — SQL, права режет — сервис license, нарушения определяет — код.

Ключевой компромисс

Один инстанс PostgreSQL/NATS и по одной реплике сервисов: изоляция данных есть, высокой доступности нет. Это осознанно зафиксировано в docs/decisions.md.

Инженерная культура

Идемпотентность на трёх уровнях (dedup-окно NATS, lease + attempt_token, processed_snapshots), единый формат ошибок, сквозной request-id, distroless-образы, откатываемый CD без реестра.

3Конвейер инвентаризации

Самая интересная часть системы: как 50-мегабайтный CSV превращается в актуальное состояние парка и не ломается при повторах, рестартах и параллельных попытках.

Почему это работает без «магии»: три уровня идемпотентности

УровеньМеханизмКакую аварию закрывает
Публикация Nats-Msg-Id = snapshot_id + окно дедупликации 2 минуты, WorkQueue retention (сообщение исчезает после Ack). Повторная публикация после сбоя не создаёт вторую задачу; очередь не растёт бесконечно.
Обработка Захват снимка UPDATE … RETURNING attempt_token с lease 120 с, heartbeat продлевает lease, финальный статус пишется только при совпадении токена. Повторная доставка после AckWait не перезаписывает результат параллельной попытки («зомби-воркер»).
Синхронизация processed_snapshots + сравнение collected_at (устаревший снимок → SUPERSEDED), upsert устройства и установок, деактивация отсутствующих только для FULL-снимка. Повтор импорта и «старый» снимок не откатывают текущее состояние ПК.
Осознанная дыра. Между записью снимка в inventory_db и публикацией в NATS нет транзакционного outbox: при падении processor в этом окне событие не уйдёт. Компенсация — авто-возобновление незавершённых импортов при старте и POST /imports/{id}/retry. Для прода это первый кандидат на доработку.

Семантика ошибок

  • Временные (сеть, недоступность license/llm, дедлок): Nak с задержкой 10 с, снимок возвращается в очередь.
  • Постоянные (invalid / not_found / forbidden / unauthenticated, несовпадение serial): Term — сообщение не крутится вечно, снимок FAILED.
  • Исчерпаны попытки (5 доставок): GiveUp помечает снимок статусом FAILED с причиной; импорт получает COMPLETED_WITH_ERRORS.
  • Ошибка LLM не является ошибкой снимка — ПО уходит в ручную проверку. Это правильное продуктовое решение: доступность конвейера не зависит от доступности модели.

4Smart Matching: каскад дешёвых шагов перед LLM

Кейс А хакатона — «грязные» имена из ОС (studio_visual_2022.exe, Google_Chrome_v2) нужно связать с официальным каталогом. Решение — не «отправить всё в модель», а воронка.

Что здесь архитектурно правильно. Модель не генерирует сущность, а выбирает из множества, построенного БД, и её ответ проходит валидацию (id из кандидатов + порог уверенности). Это убирает целый класс галлюцинаций и делает результат воспроизводимым. Плюс каждый успешный ответ становится alias — то есть система со временем перестаёт нуждаться в модели для тех же строк.

Цена решения

  • Слабые кандидаты. Для Microsoft Visual Studio 2022 pg_trgm может вернуть одного кандидата из-за похожести редакций — строка уйдёт на ручную проверку. Это зафиксировано в известных ограничениях.
  • Локальный кэш. LRU живёт в процессе worker: после правки alias в license старое значение доживает до TTL (10 минут). При масштабировании worker'ов кэш надо выносить в Redis и инвалидировать событием.
  • Пороги — компромисс. 0.95/0.10 для авто-fuzzy и 0.85 для LLM означают «лучше отправить человеку, чем ошибиться в учёте лицензий». Для SAM это правильная асимметрия: ложное совпадение искажает баланс и создаёт юридический риск.

5AI-ассистент и границы доверия

Кейс В хакатона: «У кого стоит нелицензионный Photoshop?», «Сколько лицензий простаивает?». Реализовано не как Text-to-SQL, а как набор разрешённых инструментов поверх обычного API.

Почему инструменты, а не генерация SQL

Безопасность

Модель физически не может обратиться к БД. Каждый инструмент — вызов RunQuery в license с токеном пользователя. Инъекция в промпт не расширяет права: их режет сервис.

Детерминированность

Считает SQL, а не токены модели. Ответ на «сколько лицензий простаивает» совпадает с цифрой на дашборде — потому что это один и тот же код.

Переиспользование

Тот же механизм обслуживает UI (GET /api/v1/data/{dataset}) и экспорт (POST /api/v1/export → XLSX). Одна реализация — три потребителя.

Управляемость

Набор датасетов, колонок и фильтров — это код, его можно ревьюить и тестировать. Промпт может врать, whitelist — нет.

Межсервисная аутентификация. Служебные вызовы подписываются HS256-токенами с отдельным issuer sam-internal и сервисными ролями (INVENTORY_WORKER, CHAT_SERVICE, LLM_SERVICE, LICENSE_SERVICE). Пользовательским токеном сервисную роль получить нельзя. Когда вызов идёт «от имени пользователя», пробрасывается именно пользовательский токен — и license применяет его роль.

Ограничители, которые защищают бюджет и стенд

  • Семафор LLM_MAX_CONCURRENT_REQUESTS=1 — по одному запросу к провайдеру (GigaChat лимитирует).
  • Дневной бюджет 500 000 токенов, таймаут 45 с, ≤ 5 итераций инструментов, обрезка результата до 12 000 байт.
  • Один активный запрос на пользователя в chat и rate limit 30 r/min на шлюзе.
  • Честный отказ: инструмент get_data_capabilities прямо сообщает модели, что в системе нет перечня обязательного ПО по рабочим местам — это снимает целый класс галлюцинаций «недостающие программы».
Бюджет токенов и «один активный запрос» хранятся в памяти процесса. При двух репликах chat/llm лимиты начнут считаться отдельно на каждую, а после рестарта обнулятся. Для прода — вынести в Redis или PostgreSQL.

6AI-анализ лицензионных соглашений (EULA)

Кейс Б: загрузить длинный текст соглашения и получить ключевые риски — можно ли использовать в коммерческих целях, есть ли скрытые подписки. Ключевое правило: AI предлагает, человек утверждает.

7Compliance Engine — детерминированное ядро

Здесь LLM нет вообще, и это принципиально: нарушения должны быть воспроизводимыми и объяснимыми.

Тип находкиУсловиеКомментарий
FORBIDDEN_SOFTWAREУстановлен продукт со статусом «Запрещённое» (статус требует комментария — причины запрета).Юридический/ИБ-риск, самый высокий severity.
OUTDATED_SOFTWAREУстановленная версия ниже актуальной в каталоге или продукт в статусе «Устаревшее».Требует корректной версии в каталоге — данные ведёт администратор.
LICENSE_DEFICITУстановлено на большем числе устройств, чем мест в действующих договорах. Для платного ПО без действующих договоров дефицит = число устройств.Тот самый «штрафной риск: Office на 120 ПК при 100 лицензиях».

Инженерные свойства

  • Стабильный finding_key: повторный расчёт делает upsert, исчезнувшее нарушение → RESOLVED, подтверждённое админом остаётся ACKNOWLEDGED. История не теряется и дублей нет.
  • Advisory-локи по продуктам при пересчёте: параллельные синхронизации разных ПК не устраивают гонку в балансе лицензий.
  • Триггеры пересчёта: синхронизация инвентаря, изменение каталога/лицензий/соглашений, ручной запуск и периодическая проверка раз в час (истечение сроков договоров).
  • Нераспознанное ПО — не нарушение, а задача в очереди сопоставления. Продуктово верно: нельзя штрафовать пользователя за то, что система не смогла распознать строку.
  • Честная метрика CONCURRENT: по данным установок нельзя узнать одновременное использование, поэтому такие балансы помечаются UNSUPPORTED_METRIC, а не выдумываются.

9.1. Платформа бэкенда

СлойВыборПочему именно такАльтернативы и цена решения
Язык и рантаймGo 1.26, CGO выключен, статический бинарник Задача — I/O и конкурентность: приём 50 МБ файла, пул парсеров, pull-consumer с heartbeat, SSE-стримы, параллельные gRPC. Горутины и errgroup дают это без фреймворков. Один бинарник без рантайма идеально ложится в distroless, стартует за миллисекунды, ест десятки мегабайт. Python/FastAPI — быстрее писать AI-обвязку, но хуже с CPU-парсингом и памятью на большом CSV, тяжелее образ. Node/TS — один язык с фронтом, но потоковый парсинг и типобезопасность домена слабее. Java/Spring — избыточен по памяти для шести сервисов на одной ВМ. Цена Go: больше кода вручную (~14,7 тыс. строк), нет ORM «из коробки».
Организация кодаМонорепо, один модуль sam, services/<name>/internal/… Общие pkg/* без версионирования и публикации, атомарная правка контракта и всех потребителей одним коммитом, одна команда go build ./.... При этом каждый сервис имеет свой Dockerfile и собирается независимо. Полирепо — независимые релизы, но версионирование общих библиотек и синхронизация proto на хакатоне съели бы время. Цена монорепо: связанность (правка pkg требует пересборки всех) — смягчено раздельными CD-пайплайнами.
Слои внутри сервисаdomain · service · repository · transport · platform · app Домен без внешних зависимостей (правила комплаенса и сопоставления — чистые функции, их видно и можно проверить), сервисный слой — сценарии и RBAC, транспорт — HTTP/gRPC, platform — клиенты соседних сервисов. Зависимости направлены внутрь, замена адаптера не трогает правила. Плоский «handler + SQL» был бы быстрее на старте, но правила комплаенса расползлись бы по HTTP-хендлерам. Цена: бойлерплейт и одинаковые скелеты в пяти сервисах.
HTTPchi v5 поверх net/http Тонкий роутер: группы, middleware (timeout, recoverer, request-logger), совместимость со стандартным http.Handler — SSE и потоковая загрузка пишутся руками без борьбы с фреймворком. gin/echo/fiber — свой контекст и больше магии; stdlib ServeMux — можно, но группы и middleware пришлось бы писать самим. Цена: минимальная, chi почти не навязывает стиль.
Конфигурацияcaarlos0/env + buildconfig (запечатанный JSON) Типизированный парсинг env со значениями по умолчанию; в проде — конфиг внутри бинарника, чтобы на сервере не было файла с секретами и чтобы конфигурация откатывалась вместе с релизом. Viper + файлы — тяжёлая зависимость и «где мой конфиг» в контейнере; Vault/секреты оркестратора — правильно для прода, но требует инфраструктуры. Цена: смена настройки = пересборка образа.
Логи и наблюдаемостьslog (JSON) + сквозной x-request-id, /healthz и /readyz Стандартная библиотека вместо стороннего логгера, единый request-id проходит HTTP → gRPC metadata → логи. Readiness проверяет реальные зависимости (БД, NATS, соседние gRPC), а не «процесс жив». zap/zerolog — быстрее, но лишняя зависимость. Цена текущего выбора: нет метрик Prometheus и трассировки — это зафиксированный долг, а не забывчивость.

9.2. Данные и транспорт

СлойВыборПочему именно такАльтернативы и цена решения
СУБДPostgreSQL 17 + pg_trgm Нужны одновременно: транзакции и advisory-локи (баланс лицензий), нечёткий поиск по именам ПО и текстам соглашений (GIN + gin_trgm_ops), агрегаты для дашборда, JSONB для заключений EULA. Всё это — одна СУБД, без отдельного поискового кластера. Elasticsearch/OpenSearch для мэтчинга — отдельный кластер, синхронизация, эксплуатация; для десятков тысяч строк pg_trgm достаточно. MySQL — нет pg_trgm и advisory-локов в таком виде. Цена: нечёткий поиск на триграммах слабее семантического (см. проблему редакций Visual Studio).
Доступ к БДpgx v5 (пул) + goose с embed Нативный протокол и явный SQL — критично для data explorer с белыми списками и для транзакционной синхронизации. Миграции внутри бинарника применяются при старте под session advisory-локом: нет отдельного шага деплоя и безопасно при нескольких репликах. GORM/sqlc — ORM прячет SQL (а здесь SQL и есть продукт), sqlc подошёл бы, но добавил бы кодген. Цена: SQL пишется руками, миграции необратимы при откате релиза — нужен обратно совместимый DDL.
Изоляция данныхТри БД в одном инстансе, три пользователя Логическое «database per service» без трёх кластеров: сервис не может прочитать чужие таблицы, у каждого свои миграции и свой пользователь. Экономия памяти и эксплуатационных расходов на одной ВМ. Одна схема на всех — быстрее, но убивает границу владения; три кластера — правильная изоляция, но неоправданно для MVP. Цена: общий инстанс = общая точка отказа и общий ресурс.
Асинхронный транспортNATS JetStream, поток INVENTORY (WorkQueue, file) Нужны: очередь задач с подтверждением, повторы с ограничением попыток, backpressure, дедупликация публикации и переживание рестарта. JetStream даёт всё это одним бинарником: AckWait, MaxDeliver, MaxAckPending, Nats-Msg-Id, WorkQueue-retention (сообщение уходит после Ack). Kafka — избыточен: партиции, retention-политики, отдельная эксплуатация ради одного потока; RabbitMQ — сопоставим, но дедупликацию пришлось бы делать самим; Redis Streams — проще, но слабее семантика повторов/дедупа. Цена: команда должна знать JetStream (нюансы Ack/Term/Nak).
Синхронный транспортgRPC + protobuf (buf, пакеты *.v1) Строгий контракт между сервисами, версионирование, кодогенерация для Go, server-streaming для ответов ассистента, единый маппинг ошибок в apperr, retry-политика на UNAVAILABLE и проброс метаданных (токен, request-id) — всё в одном механизме. Внутренний REST — проще на старте, но нетипизированный контракт и ручной стриминг. Цена: нужен codegen (make proto через go run, локальная установка buf не нужна) и внутри сети gRPC без TLS — доверие построено на изоляции docker-сети.
Шлюзnginx, а не собственный API-сервис Маршрутизация, лимиты тела и частоты, CORS, request-id, статика Swagger — это конфигурация, а не код. Отдельный сервис-шлюз добавил бы сетевой хоп, точку отказа и соблазн вынести туда авторизацию. Kong/Traefik/Envoy — динамика и сервис-дискавери, но тяжелее; свой Go-gateway — лишний код. Цена: нет динамического роутинга, апстримы резолвятся через Docker DNS (resolve + keepalive).
Кэшhashicorp/golang-lru (expirable) + singleflight В парке тысячи одинаковых строк ПО: LRU на 10 000 ключей с TTL 600 с снимает основную нагрузку с license и LLM, singleflight не даёт «стаду» одинаковых запросов к модели. Redis — общий кэш и инвалидирование по событию, но ещё один компонент. Цена локального кэша: устаревшие alias до 10 минут и отсутствие общего кэша при масштабировании worker'ов.

9.3. Безопасность и AI

СлойВыборПочему именно такАльтернативы и цена решения
АутентификацияВнешний IdP + RS256 в каждом сервисе; межсервисные HS256 По ТЗ IdP внешний: сервисы не хранят пароли и только проверяют подпись публичным ключом. Асимметрия позволяет раздавать ключ всем сервисам без риска подделки. Служебные токены — отдельный issuer и сервисные роли, ротация одним секретом; пользовательским токеном сервисную роль не получить. Сессии/куки — сложнее для API и агента; общий HS256 для всех — любой сервис смог бы выпустить пользовательский токен. Цена: два механизма и аккуратный проброс контекста.
АвторизацияRBAC в сервисном слое license + scope в SQL, allowlist инструментов в llm Данные режутся там, где они живут. Промпт — не граница безопасности: даже успешная prompt-инъекция упирается в роль токена. Один и тот же код обслуживает UI, экспорт и ассистента. Авторизация на шлюзе — обходится прямым вызовом внутри сети; права в промпте — обходится формулировкой вопроса. Цена: дублирование проверок в HTTP- и gRPC-транспортах.
LLM-провайдерGigaChat (основной), OpenAI-compatible, mock по умолчанию Российский контур: GigaChat доступен без зарубежных карт, поддерживает function calling и русский язык, работает с сертификатом НУЦ Минцифры. Абстракция провайдера делает модель конфигурацией, а mock позволяет поднять весь стек без ключей и получить детерминированное демо ([DEMO]). OpenAI/Claude — сильнее в рассуждениях, но недоступны в контуре заказчика; локальная модель — нужен GPU. Цена GigaChat: OAuth с кэшем токена и повтором на 401, отдельный CA, жёсткие лимиты (отсюда семафор = 1 и retry на 429), Ultra требует нового адреса API.
Данные для моделиИнструменты + белые списки вместо Text-to-SQL Модель выбирает датасет, фильтры и группировку из разрешённого набора; SQL собирает сервис, агрегацию делает БД. Ответ детерминирован, объясним и совпадает с дашбордом. Генерация SQL моделью — гибче для произвольных вопросов, но инъекции, галлюцинации и обход RBAC; RAG по документам — не отвечает на «сколько лицензий простаивает». Цена: набор датасетов фиксирован, новый вопрос требует доработки кода.
Стриминг ответаSSE (chat → браузер) + gRPC-stream (llm → chat) Поток односторонний, работает через обычные прокси, не требует отдельного протокола и состояния соединения; в браузере — простой парсер событий. Достаточно для «печатается ответ». WebSocket — двунаправленность не нужна, а прокси-настройка и состояние сложнее; long polling — задержки и лишние запросы. Цена: нужны proxy_buffering off и длинные таймауты (сделано в nginx).
Промптыembed + версии (matching-v1, eula-v1) Промпт — часть контракта: он версионируется вместе с кодом, а заключение EULA кэшируется по хэшу текста и версии промпта. Смена промпта автоматически инвалидирует кэш. Промпты в БД/внешнем сервисе — правки без релиза, но теряется воспроизводимость и ревью. Цена: изменение промпта требует сборки.

9.4. Эксплуатация и поставка

СлойВыборПочему именно такАльтернативы и цена решения
ОркестрацияDocker Compose, а не Kubernetes Один сервер, семь контейнеров, необходимости в автоскейлинге нет. Compose даёт детерминированный стек, healthcheck-зависимости и простой откат. Kubernetes на хакатоне — недели инфраструктуры вместо продукта. k8s/Nomad — HA и rollout из коробки, но несоразмерная сложность. Цена: нет HA и автоскейлинга, масштабирование worker'ов — вручную (WORKER_REPLICAS).
Образыmulti-stage → distroless static nonroot, -trimpath -ldflags="-s -w" Минимальная поверхность атаки: нет shell, пакетного менеджера и лишних бинарников; процесс не root. HEALTHCHECK сделан подкомандой того же бинарника — иначе в distroless нечем проверять здоровье. alpine — есть shell (удобно отлаживать), но больше CVE-поверхность; scratch — то же, что distroless, но без CA-сертификатов и nonroot-пользователя. Цена: нельзя «зайти в контейнер и посмотреть».
ДоставкаCD без реестра: bake → tar-артефакт → SSH → docker load → compose up --wait Нет приватного registry и бюджета на него; артефакт GitHub Actions — готовое хранилище релизов. Релиз атомарен: образы + compose + манифест едут вместе, checksum проверяется, место на диске проверяется заранее. GHCR/Docker Hub + pull на сервере — стандартнее и легче по трафику, но нужен реестр и доступы. Цена: большие артефакты, доставка только на один хост, инфраструктурные образы должны быть заранее.
Инструмент деплояСобственная Go-утилита в .github/scripts/release с тестами Один статический бинарник и на runner, и на сервере — без bash-зоопарка и зависимостей. Логика (lock, pending-состояние, откат, сборка мусора, хранение двух релизов) покрыта тестами и проверяется в CI. Ansible/bash — быстрее написать, но труднее сделать идемпотентно и протестировать. Цена: ~1000 строк собственного кода, который тоже надо поддерживать.
Контракт APIOpenAPI в репозитории + Swagger UI локально (вендор) Единый источник правды для фронта и ревью; документация работает без интернета и без авторизации, при этом сами ручки остаются защищёнными. Генерация из кода — меньше рассинхрона, но нужен инструмент; сейчас спецификация ведётся вручную, и это риск дрейфа. Цена: спеку надо не забывать обновлять.
Прикладные утилитыСвой XLSX- writer и doctext на stdlib Экспорт — одна таблица (шапка + строки): 150 строк zip/XML вместо тяжёлой зависимости. Разбор PDF/DOCX — библиотека + stdlib, без внешних бинарников, что критично для distroless. excelize — богаче (стили, формулы), но большая зависимость; tika/pandoc — не положить в distroless. Цена: нет стилей и формул в экспорте, PDF со сложной вёрсткой может извлекаться плохо.
Общая логика выбора. Стек последовательно оптимизирован под три ограничения хакатона: один сервер, российский контур и демо без ключей. Отсюда Go + Compose + один PostgreSQL + NATS вместо Kafka + GigaChat с mock по умолчанию + доставка без реестра. Каждое «упрощение» зафиксировано вместе с его ценой — это редкая и правильная инженерная дисциплина.

10Фронтенд: архитектура и обоснование

SPA на React 19 + TypeScript, ~6 200 строк исходников и ~3 000 строк сгенерированного клиента. Ключевая особенность — типизированный клиент генерируется из живого OpenAPI, а состояние привязано к «эпохе сессии», чтобы переключение роли не показывало чужие данные.

ВыборПочемуЦена / альтернатива
SPA (Vite), не SSR/Next.js Админка за авторизацией: SEO не нужен, серверный рендеринг не нужен, статика отдаётся nginx и кэшируется навечно. Меньше инфраструктуры — нет Node-сервера в проде. Первый рендер требует загрузки бандла; смягчено авто-кодсплитом маршрутов.
TanStack Router Файловые маршруты с типизированными параметрами и поисковыми строками, loader-ы и guards до предзагрузки — ролевые разделы закрыты на уровне маршрутизации (_authenticated, _admin). Молодая экосистема и генерация routeTree; альтернатива React Router — меньше типобезопасности.
TanStack Query Кэш, инвалидация, отмена и повторы из коробки. Ключ кэша включает роль и «эпоху» сессии — это решает реальную проблему демо: переключил роль и не увидел данные предыдущей. Требует дисциплины в ключах; альтернатива — ручной стор и гонки запросов.
Кодогенерация клиента (apicraft) OpenAPI — единственный источник правды: типы ответов и параметры приходят из контракта, ручных fetch-обёрток нет, рассинхрон с бэкендом ловится на typecheck. Генерация зависит от доступности стенда; при изменении контракта нужна перегенерация.
Tailwind 4 + shadcn / Base UI Скорость сборки интерфейсов и доступность «из коробки» (фокус, клавиатура, ARIA) без собственной дизайн-системы — критично, когда UI делает один человек за дни. Зависимость от версий компонент-библиотеки; альтернатива — MUI/AntD с более тяжёлым стилем.
zod + react-hook-form Валидация форм каталога, договоров и устройств на клиенте с типами из схемы; сервер всё равно проверяет заново. Двойная валидация (клиент + сервер) — осознанное дублирование ради UX.
Один Axios-инстанс Токен, отмена, нормализованные ошибки и обработка 401 в одном месте; компоненты не знают про HTTP. Собственная логика «эпох» нетривиальна; альтернатива fetch + обёртки — то же самое, но вручную.
Reverse proxy вместо CORS И в dev (vite), и в проде (nginx) /api/v1 проксируется на бэкенд: браузер видит один origin, CORS-проблем нет, токен не уходит на сторонний домен. Адрес бэкенда зашит в конфиг прокси — для другого стенда его надо параметризовать.

11Сильные стороны, риски и техдолг

Что сделано заметно лучше среднего хакатон-проекта

1. Идемпотентность сквозная

Дедуп NATS + lease/attempt_token + processed_snapshots + finding_key. Это уровень продакшн-размышлений, а не демо.

2. LLM в клетке

Выбор из кандидатов, валидация ответа, allowlist инструментов, лимиты токенов и итераций, деградация в ручную проверку.

3. RBAC там, где данные

Проброс пользовательского JWT через два сервиса и фильтрация в SQL — обход промпта не даёт данных.

4. Единый контракт ошибок

{error:{code,message,request_id}}, маппинг kind → HTTP/gRPC, пагинация page/limit — фронт предсказуем.

5. Откатываемый деплой

Атомарный релиз, checksum, preflight диска, --wait, verify по HTTPS, автоматический rollback, два успешных релиза.

6. Честность модели

get_data_capabilities и UNSUPPORTED_METRIC — система прямо говорит, чего она не знает, вместо галлюцинаций.

7. Документированные решения

docs/decisions.md: 21 решение с обоснованием и отдельный список известных ограничений. Редкость.

8. Наблюдаемость на минималках, но сквозная

request-id из nginx проходит через HTTP и gRPC в логи всех сервисов; readiness проверяет зависимости.

Риски и что бы я сделал в первую очередь

ПриоритетРискПоследствиеРекомендация
P1Нет transactional outbox между inventory_db и NATS Падение processor в окне «записал снимок — не опубликовал» теряет задачу; сейчас спасает авто-возобновление и retry. Таблица outbox в той же транзакции + отдельный publisher-луп (или Debezium/CDC). Это же снимает нагрузку на компенсационные механизмы.
P1По одному экземпляру PostgreSQL, NATS и сервисов Любой сбой — полный простой; потеря тома postgres = потеря учёта. Бэкапы PostgreSQL (WAL/PITR) прежде всего, затем реплики сервисов за nginx и NATS-кластер. Compose уже поддерживает WORKER_REPLICAS.
P1Секреты запечатаны в образ, один JWT_SERVICE_SECRET на все сервисы Утечка образа = утечка конфигурации; ротация секрета требует пересборки всех сервисов. Docker secrets / sops / Vault, отдельные секреты на сервис, короткоживущие сервисные токены. Публичный PEM внутри образа — нормально, секреты — нет.
P1Демо-JWT захардкожены во фронте, refresh отсутствует Для стенда допустимо, для прода — фактически вечный публичный доступ. Подключить внешний IdP (OIDC + PKCE), убрать токены из репозитория, оставить демо-режим только для локального стенда.
P2Бюджет токенов и «один активный запрос» — в памяти процесса При масштабировании лимиты обходятся, после рестарта обнуляются. Redis или таблица в PostgreSQL со счётчиком на пользователя/сутки; распределённая блокировка активного запроса.
P2QueryData для ADMIN считает баланс по всему каталогу на каждый запрос Каждая страница установок тянет полный расчёт балансов — рост стоимости с ростом парка. Материализованное представление баланса с обновлением при пересчёте комплаенса либо кэш на короткий TTL.
P2Локальный LRU-кэш сопоставлений (TTL 600 с) После правки alias worker до 10 минут использует старое решение; при нескольких репликах кэши расходятся. Общий кэш + инвалидирование по событию изменения alias (NATS уже есть).
P2Нет метрик и трассировки Инциденты разбираются по логам; узкие места (LLM, батчи, комплаенс) не видны численно. Prometheus-метрики (латентность ручек, длина очереди, доля UNKNOWN, токены/сутки) + OpenTelemetry поверх уже существующего request-id.
P2Группировка CSV в памяти 50 МБ укладываются, но лимит жёсткий: файл на порядок больше упрётся в память. Потоковая группировка по отсортированному ключу или внешняя сортировка; лимит тела оставить как защиту.
P3gRPC внутри сети без TLS Доверие построено на изоляции docker-сети; при переезде на несколько хостов трафик пойдёт открытым. mTLS или service mesh при выходе за пределы одного хоста.
P3Адрес бэкенда зашит в прокси фронта и в apicraft-конфиг Развернуть другой стенд без правки исходников нельзя. Параметризовать через переменную окружения сборки/шаблон nginx.
P3Метрика CONCURRENT не проверяется, агент не аутентифицируется отдельно Часть лицензионных моделей остаётся вне контроля; роль INVENTORY_AGENT объявлена, но не используется. Источник данных о сессиях (агент/терминальный сервер) и отдельный клиентский токен для агента.

Итог архитектора. Это цельная, объяснимая система с правильно расставленными границами: дешёвая детерминированная логика впереди дорогой вероятностной, права — на стороне данных, надёжность — на стороне конвейера. Основные долги (outbox, HA, внешние счётчики лимитов, метрики) лежат ровно там, где и должны лежать у MVP, собранного за хакатон, и все они локализованы: их можно закрывать по одному, не переписывая архитектуру.
