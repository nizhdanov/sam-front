## 1. Цель проекта и ожидаемый результат

Разработать интерфейс управления программными активами: каталог ПО и соглашений, договоры закупки, импорт инвентаризаций, устройства и установки, контроль лицензий и нарушений. После MVP добавить Smart Matching, анализ соглашений и чат, используя существующий backend.

Результат исходного планирования — этот исполняемый план. При планировании исходный код, конфигурация и зависимости не изменялись; результаты реализации фиксируются у соответствующего этапа. Чекбокс задачи отмечается только после реализации и указанной проверки; наличие экрана с демонстрационными данными не означает завершения интеграции.

**Согласовано с заказчиком в текущей сессии:** рабочая основа — API v2, роли `ADMIN`/`USER`, учёт по устройствам, факты установок поступают только из CSV. Противоречащие этому упоминания сотрудников, ИТ-директора и ручного ввода установок сохранены в разделе 12 как расхождения, но не включены в реализацию.

**Уточнение заказчика от 15 ноября 2026 года:** для MVP авторизация захардкожена: существующий shadcn Select с вариантами **«Пользователь» (`USER`) | «Администратор» (`ADMIN`)** записывает соответствующий заранее заданный демонстрационный токен в **`localStorage` под ключом `token`**. IdP, форма входа, callback, refresh и logout не входят в MVP и не блокируют его разработку. Интерфейс чатбота строится на **shadcn AI Elements** с переиспользованием уже добавленных chat-компонентов. Эти уточнения имеют приоритет над прежним описанием входа; обновлены архитектура, задачи и приёмка, а не только добавлено примечание.

MVP должен позволять пройти цепочку: соглашение → продукт → договор → CSV → устройство/установки → баланс/нарушения → обработка нарушения → журнал. Обычный пользователь получает разрешённый backend каталог и данные своего устройства. Отдельный результат после MVP — работающие ИИ-сценарии, а не локальные имитации ответов.

## 4. Область разработки и ограничения

### 4.1. Обязательный frontend MVP

Переключатель ролей «Пользователь | Администратор» с записью `localStorage.token`, меню и guards; каталог и карточки продуктов; справочник соглашений; реестр и ведение договоров; импорт CSV с подтверждением и отчётом; устройства и их установки; KPI, баланс и нарушения; обработка нарушения с комментарием; журнал; просмотр своего устройства и рисков для USER. Версии продукта входят в карточку, поскольку нужны для актуальности и US-03/US-12. Реальный вход через IdP не требуется.

### 4.2. Отдельная очередь после MVP

US-14–US-19 и US-21: мэтчинг, правила и пороги, анализ EULA, рекомендации похожих соглашений, чат обеих ролей, история и XLSX. В REQUIRMENTS.md ИИ обозначен дополнительной частью: эти задачи не блокируют приёмку базового MVP. Полное покрытие всех User Stories требует выполнения и этой очереди.

### 4.3. Границы

- Backend, БД, CSV-дедупликация, исключение KB, нормализация, расчёт лицензий, контроль прав и вызовы LLM принадлежат серверу. В плане frontend не подменяет их локальной бизнес-логикой.
- MVP использует явно заданные демонстрационные токены двух ролей. Select переключает выбранный контекст, но сам не выдаёт права backend: реальные API-запросы должны приниматься с соответствующим токеном. Обе роли доступны участнику демонстрации; это ограничение выбранного прототипа, а не полноценная аутентификация сотрудников.
- Отдельного справочника сотрудников, роли ИТ-директора, ручного создания/удаления установок и устройств не будет: это согласованное уточнение исходных требований.
- Количество купленных мест изменяется договорами, а не полем продукта. Цены отсутствуют; показывать простаивающие места, без выдуманной экономии в рублях и без утверждения о фактическом неиспользовании ПО.
- `in_bpo`, `license_type` и `cost_model` — независимые признаки. БПО не тождественно бесплатности, Open Source не тождественно разрешённости коммерческого использования.
- Метрики `UNLIMITED`, `CONCURRENT`, `UNKNOWN` нельзя самостоятельно пересчитывать как `PER_DEVICE`. Неизвестное покрытие показывать как неизвестное, а не как ноль или отсутствие риска.
- API не предоставляет серверную сортировку большинства списков. Не отправлять придуманный `sort`; при сортировке загруженного набора явно обозначать её область.
- Не строить новую дизайн-систему, универсальный CRUD-конструктор, глобальный store, backend, клиентский LLM, редактор классификатора или систему уведомлений.

### 7.2. Основные потоки

1. **Каталог:** ADMIN создаёт соглашение → продукт с привязкой к нему → версию → договор. После сохранения обновляются список и карточка; ошибка сохраняет введённые поля. Удаление с подтверждением; 409 оставляет объект на месте и предлагает доступный вариант — например, архив продукта.
2. **CSV:** выбрать `.csv` → проверить размер/дату → `POST /imports` с `confirm=false` → показать серверные первые 20 строк, исключения и ошибки → подтвердить или отменить → опрашивать статус → показать загруженные/дубли/KB/ошибки и результаты устройств. Переход со страницы не отменяет обработку; открытие URL восстанавливает её состояние.
3. **Комплаенс:** KPI → список с фильтром → продукт → устройства с установкой → конкретное нарушение → комментарий «обработано» → повторное чтение списка и журнала. ACKNOWLEDGED означает подтверждение обработки, не фактическое удаление ПО и не RESOLVED.
4. **USER:** восстановление выбранной роли или Select «Пользователь» → каталог с разрешённой сервером областью → продукт; «Мой компьютер» → свои установки → запрет/устаревание → актуальная версия. Нет device_serial в стендовом токене — объяснить, что компьютер не привязан; не давать ручной выбор чужого устройства. Select «Администратор» переводит в административный контекст по порядку раздела 8.6.
5. **Мэтчинг:** неизвестная установка → очередь → кандидат или другой продукт/версия → принятие/отказ → обновить правила, установки и комплаенс. Автоприменение новых правил проверяется следующим CSV.
6. **EULA:** создать/открыть соглашение → вставить текст или загрузить файл → явно запустить анализ → изучить условия/риски с абзацами → просмотреть похожие соглашения → явно сохранить выводы. Анализ сам по себе не меняет тип лицензии.
7. **Чат:** создать/открыть диалог → типовой или свой вопрос → потоковый Markdown → переход по разрешённой sam-ссылке → экспорт выбранной таблицы → возврат к сохранённому диалогу. Незавершённый поток остаётся обозначенным как незавершённый.

## 8. Архитектура frontend

### 8.1. Ответственность и файлы

- `src/app`: оставить bootstrap/router; добавить небольшой auth-модуль с таблицей демонстрационных ролей/токенов и текущим контекстом. Передавать роль, состояние готовности/смены и QueryClient в router context для guards/loaders; не создавать IdP-интеграцию.
- `src/routes`: тонкие файлы маршрутов, `validateSearch`, `beforeLoad`, связывание со страницами. Pathless layout `_authenticated` проверяет готовность локального контекста, вложенный `_admin` — роль. `/` перенаправляет по восстановленной роли. При ошибке токена остаётся доступен селект, без отдельного login/callback маршрута. Route tree генерируется существующим инструментом.
- `src/features/<module>`: по мере реализации добавлять страницы, формы, query options и схемы конкретного модуля: software, agreements, contracts, imports, devices, compliance, matching, chat, audit. Не создавать пустые папки или обязательные обёртки для каждой операции.
- `src/components/ui`: сохранить текущие примитивы, включая Select/MessageScroller/Message/Bubble/InputGroup. Недостающие Dialog/Tabs/Badge/Alert/Empty/Skeleton/Spinner добавлять только при первом использовании через shadcn и явный официальный registry. Чат — композиция shadcn AI Elements на этих компонентах. Base UI использует `render`, не Radix `asChild`.
- `src/components/layout` и `src/components/shared`: оболочка, навигация, состояние запроса, ограниченная общая таблица DataTable и экспорт. Без универсальной платформы форм/CRUD.
- `src/utils/lib/instance.ts`: сохраняет создание Axios и единственный request interceptor с чтением `localStorage.token`; дополняется только необходимой обработкой отсутствующего токена/ошибок. `src/utils/api`: безопасное чтение ошибок, адаптер data-фильтров и скачивание файлов. SSE-клиент в chat читает тот же ключ напрямую, поскольку fetch не проходит через Axios interceptor.
- `src/utils/lib/queryClient.ts`: сохранить единственный QueryClient. Generated импортировать через `@/generated/*`; остальное через `@/*`. Не переносить и не переписывать уже работающий bootstrap.

Страницы владеют конкретными запросами и формами; общие компоненты не знают бизнес-правил. API-функции generated не копируются в ручной REST-клиент. Read DTO выводятся из generated; неизвестные ответы валидируются на границе после уточнения схем, без `as SomeDTO` и без `any` для обхода неопределённости.

### 8.2. Состояние, URL и кеш

- Query хранит серверные объекты; react-hook-form — поля формы; useState — открытый диалог/строка/черновик; небольшой Context — выбранную демонстрационную роль и состояние её переключения. Redux/Zustand не нужны.
- Фильтры, группировка, вид commercial/free и page/limit отражаются в URL через Zod + `validateSearch`. Пустые значения не отправляются; смена фильтра сбрасывает page. `false` для recognized/in_bpo сохраняется как явное значение.
- Ключи запросов содержат ресурс, идентификатор и все нормализованные параметры. Область кеша включает выбранную роль и номер текущего контекста; отдельных пользовательских профилей у двух демонстрационных токенов нет. JWT в ключи не помещать.
- Для пагинируемых API — page с 1, limit 1–200, по умолчанию 50. Для `/data/*` другой протокол: `columns/rows/total/shown`, default limit 100, без page/offset; общий paginator к нему неприменим.
- При смене роли отменить запросы/потоки и очистить кеш до показа новых страниц по порядку из раздела 8.6. В localStorage по требованию хранится только `token`; роль восстанавливается сопоставлением с таблицей токенов. Административные ответы, чат и Query cache туда не сохранять.
- Существующие 30 секунд staleTime оставить. Query cancellation передавать через `config.signal`; GET можно ограниченно повторять при сети/5xx, но не при 400/401/403/404/409/413/429. Мутации, анализ и отправка чата автоматически не повторяются.
- После успешной мутации инвалидировать минимальные затронутые ключи согласно разделу 9. Не дублировать серверные расчёты optimistic update. При сомнительном результате сетевого сбоя сначала перечитать объект/импорт/диалог.

### 8.4. Состояния, ошибки и доступность

Для каждого списка: initial loading, пустая база с разрешённым CTA, пустой результат фильтра со сбросом, ошибка с повтором, данные с фоновым обновлением. Не превращать ошибку в «0 объектов». Отсутствующее nullable значение — «Не указано»; отсутствующее обязательное для действия поле — ошибка контракта и отключённое действие, без фиктивного ID.

Для мутации: idle/pending/success/error; сетевой таймаут не означает, что сервер ничего не сохранил. Подтверждения нужны для удаления/архива/деактивации, явное действие — для подтверждения CSV и применения AI-выводов.

HTTP: 400 — ошибка данных; 401 — остановить защищённые запросы текущего контекста, убрать прежние данные и показать ошибку демонстрационного токена с доступным селектом; автоматического refresh/переключения роли нет. 403 — запрет; 404 — объект недоступен; 409 — конфликт с перечитыванием; 413 — размер; 429 — ограничение запроса; 503 анализа — сервис временно недоступен. Показывать безопасные message/request_id из Error, не JWT и не необработанный stack trace. При blob-ответе с ошибкой сначала распознать JSON ошибки. Поздний 401 от отменённого старого контекста не должен сбрасывать уже выбранную новую роль.

Клавиатура, видимый focus, заголовки диалогов и возврат фокуса, семантические таблицы с caption/заголовками, текстовые статусы вместе с цветом. В мобильном виде навигация сворачивается; горизонтальный scroll только внутри таблицы; формы доступны при ширине 360px. Проверять 360/768/1440px и увеличение 200%. Существующие цвета/тёмные токены сохраняются, новая настройка темы не требуется.

### 8.5. Чат на shadcn AI Elements, Markdown и SSE

В проекте уже есть базовые chat-компоненты и `@shadcn/react` 0.3.1. Паттерны адаптируются к Vite SPA и SAM API; копировать Next.js приложение или демонстрационный AI transport не нужно.

| Часть чатбота                        | Принятое решение                                                                                                                                                                                                                                  |

| Ход диалога — паттерн Message        | Message/MessageContent; вопрос пользователя — Bubble/BubbleContent, ответ — Markdown, действия — MessageFooter                                                                                                                                    |
| Поле — паттерн Prompt Input          | Имеющиеся InputGroup/InputGroupTextarea/InputGroupAddon/InputGroupButton; Enter отправляет, Shift+Enter добавляет строку, Enter во время IME-композиции не отправляет                                                                             |
| Типовые вопросы — паттерн Suggestion | Имеющийся Button с текстом вопроса из backend; отправка через тот же обработчик и ограничения, что у формы                                                                                                                                        |

Прокруткой и возвратом к новым сообщениям управляет MessageScroller: autoScroll, anchor на вопросе, выход из автоматического следования при чтении истории. Свою математику scrollTop/useStickToBottom не писать. Новый выбранный диалог/роль сбрасывает соответствующий provider; поступление delta не пересоздаёт messageId и всю ленту. Входящие данные преобразуются в небольшой локальный view model, не в придуманный backend DTO.

Streamdown поддерживает потоковый и статический режимы, незавершённый Markdown и custom components. Во время ответа использовать `mode="streaming"` и `isAnimating`, в сохранённой завершённой истории — `mode="static"`; экспорт доступен только завершённым таблицам. Передать проверенные sam-ссылки через политику URL в custom link renderer, а table AST через custom table renderer — в существующий серверный экспорт. Встроенное скачивание таблиц отключить, чтобы не дублировать XLSX-сценарий. [Конфигурация](https://streamdown.ai/docs/configuration), [components и node](https://streamdown.ai/docs/components).

Сырой HTML и опасные URL не исполнять. `sam://device/<uuid>`, `sam://product/<uuid>`, `sam://contract/<uuid>` разбирать по точному типу/UUID и преобразовывать в TanStack Link с проверкой роли; неизвестную схему или административную цель USER не делать активной. Внешние ссылки — только http/https с безопасным открытием. Не добавлять вложения, выбор модели, reasoning/tool UI, оценки ответов или regenerate: SAM-контракт их не требует. Новая runtime-зависимость этой части — Streamdown и только необходимые ему зависимости; отдельная пара react-markdown/remark-gfm больше не планируется.

SSE — `fetch` с POST, Bearer из текущего `localStorage.token`, AbortController и потоковым TextDecoder. Fetch не получает Axios interceptor автоматически. Браузерный EventSource не поддерживает нужные POST/body/Authorization; generated метод с ответом `string` не является streaming implementation. Разбирать границы событий независимо от сетевых chunk, LF/CRLF, переносы data и UTF-8; проверять message_start/delta/message_end/error. EOF без message_end — незавершённый ответ. Смена роли прерывает чтение и отбрасывает старые delta; Abort не обещает отмену генерации на сервере, такого endpoint нет. При 429 повтор автоматически не запускать. AI SDK/useChat и его stream protocol для подключения этих UI-паттернов не требуются; SAM SSE-контракт сохраняется.

### 8.6. Демонстрационные роли и localStorage для MVP

Это окончательный контракт поведения frontend, выбранный заказчиком; отдельного проектирования входа перед TASK-004 не требуется.

- В `src/app/auth/demo-accounts.ts` сосредоточена одна таблица `USER`/`ADMIN`: русская подпись и фиксированный демонстрационный токен для каждой роли. Значения разные, переиспользуют существующий `TOKENS` без дублирования строк и проверены тестовым backend в этапе 2. Актуальность токенов и данные своего устройства учитываются в B-01. Строки `USER`/`ADMIN` сами по себе не объявляются валидными JWT.
- В оболочке всегда доступен существующий **Select**, подпись «Роль», варианты **«Пользователь» | «Администратор»** через SelectGroup/SelectItem. `onValueChange` вызывает один обработчик смены роли и `localStorage.setItem('token', выбранныйТокен)`. Ключ именно `token`; второй сохранённый ключ role не нужен.
- До первых loaders/preload/Query прочитать сохранённый token и найти точное совпадение в таблице. Известный токен восстанавливает роль. При первом запуске без token или при неизвестном значении выбрать **USER**, записать его демонстрационный токен и лишь затем разрешить запросы. Повторный reload не должен переключать сохранённый ADMIN на USER. Недоступный localStorage или незаданные токены дают понятную ошибку и блокируют запросы, а не `Bearer null`.
- При смене роли сначала скрыть прежние защищённые данные и приостановить новые запросы; отменить Query-запросы, polling и SSE, очистить кеш/активные мутации UI/черновики прежнего контекста. Увеличить номер контекста: поздние ответы и callbacks старого номера не должны менять новые экраны. Уже принятый сервером POST нельзя считать отменённым.
- Затем сохранить новый token; после успешной записи обновить роль в Context/RouterProvider, переоценить guards через router.invalidate и перейти на landing: ADMIN → `/dashboard`, USER → `/software`. Возобновить запросы только нового контекста. При ошибке записи не показывать новую роль как успешно выбранную. Axios читает актуальный ключ при каждом запросе; SSE фиксирует тот же токен на старте и отменяется при смене.
- В этой вкладке Context обновляется тем же обработчиком: событие storage здесь не возникает. В других открытых вкладках слушать storage для ключа token и применять ту же очистку/переоценку по уже сохранённому значению, без повторной записи и цикла событий. На время смены роли submit защищённых форм недоступен.
- На 401 не выполнять refresh, login redirect, автоматическое повышение роли или бесконечную перезапись дефолтного токена. Остановить защищённые данные текущего контекста и показать ошибку рядом с доступным селектом; повторный выбор роли — явное действие. Нужен новый фиксированный токен, если выданный для стенда истёк.
- Роль для меню определяется таблицей выбранных токенов, без зависимости от имени role claim IdP и без JWT-парсера. При этом backend проверяет реальную роль токена. `GET /me/device` определяет свой компьютер на сервере по device_serial демонстрационного USER; отсутствие привязки — существующее состояние 403, frontend не подставляет произвольный serial_number.

Токены двух ролей намеренно доступны участнику MVP. Это не модель production-доступа. Интеграция с настоящим IdP — отдельная будущая работа вне текущего плана реализации; она не является скрытым условием TASK-004/TASK-025.

## 9. План интеграции с backend API

### 9.1. Транспорт и авторизация

Использовать **`src/utils/lib/instance.ts`**, уже связанный с generated через `apicraft.config.ts` → `runtimeInstancePath`. Request interceptor чтения `localStorage.token` уже существует: не создавать второй instance/interceptor и не восстанавливать удалённый generated instance. Дополнить проверку отсутствующего token и общую обработку ошибок, сохраняя контракт generated запросов.

В MVP селект записывает один из двух фиксированных демонстрационных токенов по разделу 8.6; Axios добавляет `Authorization: Bearer <token>`. Fetch для SSE читает тот же ключ отдельно. API не получает строку роли вместо токена. Endpoints входа/обновления/выхода SAM не предоставляет и для выбранного MVP они не нужны. B-01 теперь означает только предоставление двух принимаемых стендом токенов и привязки собственного устройства, а не интеграцию IdP.

Настроить общий origin `/api/v1` для развёрнутого приложения; для dev — Vite proxy на согласованный backend с сохранением пути либо поддерживаемый CORS. Единственное намеренное упрощение — демонстрационные токены в auth-таблице; реальные production-учётные данные в неё не переносить. CSP/CORS/SSE buffering и таймауты reverse proxy согласовать с владельцем deployment.

Для CSV/EULA generated ожидает объект `{ file: File }`, но вызывает обычный `instance.request({ data: body })` без multipart-настройки. Через отдельный адаптер передать настоящий FormData в `config.data` без ручного boundary; проверить сеть интеграционным тестом. Нельзя считать, что наличие File в TS автоматически означает multipart.

Ответы приходят как AxiosResponse, данные лежат в `.data`. Тип ApicraftAxiosResponse объединяет success/error; выполнить корректное сужение/валидацию, не приводить ошибку к успеху. Для файлов задавать `responseType: 'blob'`, читать Content-Type/Content-Disposition безопасно, выдавать имя с fallback, освобождать object URL. Не добавлять XLSX-библиотеку: генерацию делает API.

## 10. Поэтапный план разработки

**Правило исполнения:** перед каждой задачей перечитать затронутые требования/методы, проверить актуальный diff и локальные инструкции, выполнить применимую Intent-загрузку. Менять только файлы задачи и необходимые вызовы/экспорты. Указанные проверки являются частью задачи. Backend-блокер закрывается обновлённым контрактом/подтверждённой конфигурацией и проверкой интеграции; фронтенд-заглушка его не закрывает.

**Порядок следующей сессии Codex:** выбрать первую незавершённую задачу с выполненными зависимостями → прочитать её источники и соответствующие разделы 8–9 → проверить необходимые входные данные/блокер раздела 12 → выполнить только эту задачу и её проверку → отметить чекбокс после подтверждённого результата. ## 11. Стратегия тестирования и приёмки

### 11.1. Автоматические проверки

1. На каждой реализации: `pnpm exec tsc --noEmit`, `pnpm exec eslint <изменённые исходные файлы>` без `--fix` для проверки, `pnpm build`. `pnpm lint` в текущем репозитории меняет файлы, поэтому не использовать его как read-only проверку. Форматировать только изменённые файлы.
2. Новую нетривиальную чистую логику проверять коротким тестом на установленном `node:test`/`assert`: permissions, фильтры false/null, связывание columns/rows, статусы импорта, номера абзацев, SSE, ссылки, извлечение таблиц. Пути файлов тестов перечислить в локальном test script при их появлении; не добавлять отдельную платформу тестирования для нескольких функций.
3. Fixtures должны происходить из обновлённых схем/подтверждённых ответов, без персональных данных и токенов. Они используются только в тестах, а не вместо production API.
4. Не писать snapshot-тесты каждого UI-примитива и тесты, просто повторяющие реализацию. Интеграционные и браузерные сценарии ниже выполнять вручную на доступном стенде; CI/browser runner вводить отдельным решением только при необходимости регулярного повторения.

### 12.3. Неблокирующие вопросы и технические решения

- **Классификатор:** backend хранит section/class строками. Для MVP принят ручной ввод/поиск; для дерева справочника нужен подтверждённый версионированный набор. Сайт из требований — справочный источник, не доказательство юридической актуальности классификации.
- **MB/границы дат:** подтвердить 50/10 МБ в байтах, включительность дат договоров и фильтров аудита, смысл collected_at и retry для частичных импортов. Пока UI сообщает лимит из текста контракта; серверные ограничения являются окончательными.
- **History IDs:** inventory_id в DeviceCard не объявлен import_id; карточка показывает снимок без ссылки до уточнения. Поле file_name соглашения не является URL скачивания; скачивание исходного документа не планируется без endpoint.
- **AI-сходство:** US-17 требует предложения, не обязательного слияния соглашений. Отображение Analysis.similar_agreements достаточно; persistent связь «анализ → стандартное соглашение» контрактом не задана и не добавляется.
- **Schema required:** многие описанные сущности не имеют required, хотя действия требуют идентификаторов. На границе проверять необходимые значения; не использовать non-null assertion ради действия. Уточнять required в OpenAPI при закрытии B-02.
- **Долгие запросы:** файл/анализ/чат требуют согласованных proxy timeout и SSE без буферизации. Disconnect/Abort не обещает серверную отмену; серверного cancel чата нет.
- **Экспорт:** серверу подтвердить ограничение/ошибку при превышении 10 000 строк и защиту от формул. UI не должен обозначать усечённую выгрузку полной или самостоятельно исполнять значения ячеек.
- **Стиль и инструменты:** не обновлять пакеты из-за расхождения диапазонов; установленная сборка проходит. Не выполнять `pnpm fmt`/`pretty` по всему проекту. Существующее предупреждение Field не блокирует план и исправляется отдельно только при объективной необходимости.

## 13. Итоговые критерии готовности интерфейса

### 13.1. Готовность обязательного MVP

- Выполнена TASK-025 и все её транзитивные зависимости; обязательные строки матрицы имеют проверяемый результат.
- Select «Пользователь | Администратор» меняет именно localStorage.token; после reload восстанавливается роль, при первом запуске выбирается USER. Запросы используют соответствующий фиксированный стендовый токен; 401 не вызывает refresh/redirect-loop. Смена роли очищает кеш/черновики и прерывает старые запросы, polling и SSE во всех открытых вкладках. Для MVP не требуется готовый IdP.
- ADMIN реально ведёт соглашения/продукты/версии/договоры, загружает CSV, находит устройства/установки/риски, фиксирует обработку и видит аудит.
- USER видит только разрешённый каталог и свой компьютер; ограничения подтверждены API, прямым URL, экспортом и очисткой кеша.
- Купленные места поступают из действующих договоров; дефицит, остаток, свободная лицензия и неизвестное покрытие различаются; фактическое использование и денежные суммы не выдумываются.
- CSV проходит preview/confirm/cancel/progress/report/error/retry; повторная выгрузка и KB не искажают учёт.
- Нет скрытого усечения реестров, фиктивных серверных полей, локальных «успешных» данных вместо API и незакрытых блокеров обязательных сценариев.
- Состояния, доступность, мобильная навигация и ошибки проверены; изменённые файлы проходят typecheck/ESLint, production build и применимые небольшие тесты.
